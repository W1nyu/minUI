01 — 문제

수용력은 세대마다 다른데, 인터페이스는 모두에게 같다

젊은 사용자에게 메뉴 20개는 선택지지만, 고령 사용자에게는 장애물이다. 그런데 두 집단이 같은 화면을 본다.

주목할 점은 실패 지점이 기능 수행이 아니라 기능 탐색이라는 것이다. 고령 사용자도 이체 화면에 도달하면 계좌번호를 넣고 금액을 입력하는 일은 해낸다. 막히는 곳은 그 화면까지 가는 길이다. 홈 → 전체메뉴 → 이체·출금 → 계좌이체를 지나는 동안 매 단계에서 “다음에 뭘 눌러야 하지”를 판단해야 하고, 판단이 쌓일수록 실수와 포기가 늘어난다.

문제를 발견한 계기

할아버지 태블릿을 세팅해 드리면서 안 쓰는 앱을 지우고 아이콘을 키우고 홈에 4개만 남겼더니, 그 뒤로 전화 문의가 눈에 띄게 줄었다. 기능을 더한 게 아니라 빼기만 했는데 사용성이 올라갔다. 문제는 그 작업을 내가 손으로 했다는 것이다. 가족 중에 IT를 아는 사람이 없으면 못 받는 서비스고, 무엇보다 은행 앱 안쪽 메뉴는 사용자가 정리할 방법이 없다. 이 프로젝트는 그때 손으로 한 일을 앱이 스스로 하게 만드는 것이다.

02 — 기존 해결책의 한계

간편 모드는 탐색 문제를 해결한 게 아니라 미뤄 뒀다

한계 1 · 고정 메뉴 세트

  • 기획자가 미리 정한 6~8개가 모든 사용자에게 동일하게 나간다
  • 관리비를 이체하는 사람, 연금 입금만 확인하는 사람에게 필요한 첫 화면은 서로 다르다
  • 결과적으로 누구에게도 정확히 맞지 않는다

한계 2 · 세트를 벗어나면 원점

  • 자동이체 해지, 한도 변경처럼 세트 밖 기능이 필요해지는 순간
  • “전체 메뉴로 돌아가기”를 눌러 원래의 복잡한 화면과 다시 마주한다
  • 탐색 부담이 사라진 게 아니라 뒤로 미뤄진 것

그래서 두 축이 동시에 필요하다. 하나만으로는 기존 간편 모드와 같은 자리에 머문다.

축해결하는 것없으면 생기는 일
개인화첫 화면이 그 사람에게 맞는다고정 세트 — 누구에게도 안 맞음
탐색 대체세트 밖 기능도 한 번에 도달결국 복잡한 메뉴로 회귀

03 — 설계 원칙

네 가지 원칙, 그중 하나는 개인화를 일부러 느리게 만든다

P1

보이는 것은 적게

홈 노출은 기본 4개, 최대 6개. 스크롤 없이 한 화면에 들어와야 하고, 카드 터치 영역은 최소 88×88dp.

P2

감추는 게 아니라 불러내는 것

전체 메뉴 접근성은 100% 유지한다. 화면에서 사라진 기능도 음성·검색으로 언제든 도달 가능하다. 기능을 못 쓰게 만드는 축소가 아니다.

P3

화면은 예측 가능해야 한다

사용 기록에 따라 카드가 매번 재배치되면 고령 사용자에게는 오히려 더 나쁘다. 어제 왼쪽 위에 있던 게 오늘 없으면 학습된 근육 기억이 무너진다.

P4

호스트 앱을 수정하지 않는다

엔진은 라우팅·상태·인증에 관여하지 않는다. 메뉴 카탈로그와 액션 핸들러만 주입받는다. 이식 비용이 낮아야 “어떤 앱에도 적용 가능”이 성립한다.

무엇을 포기했는가

P1과 P3를 함께 지키려면 “최신 사용 패턴을 즉각 반영하는 반응성”을 포기해야 한다. 추천 시스템 관점에서는 손해지만, 고령 사용자 대상 UI에서는 일관성이 정확도보다 중요하다고 판단했다.

04 — 핵심 기능

다섯 개 기능, 무게중심은 F3에 있다

ID기능핵심 내용
F1사용 이력 수집 메뉴 진입·완료 이벤트를 온디바이스에 기록. 메뉴 ID·시각·완료 여부만 저장하고 금액·계좌·수취인은 수집하지 않는다. 들어갔다 바로 나온 메뉴에 가중치를 주지 않기 위해 완료 여부를 함께 남긴다.
F2개인화 랭킹 빈도·최신성·상황의 가중 합으로 상위 N개 산출 (수식은 06)
F3배치 안정화 히스테리시스 20% 마진 · 하루 1회 갱신 · 변경 시 “새로 추가됨” 배지 3일 · 사용자 수동 고정(핀). 이 프로젝트에서 가장 중요한 기능.
F4음성·텍스트 탐색 발화를 받아 후보 1~3개를 큰 버튼으로 제시. 자동 실행하지 않고 사용자가 고른다.
F5콜드 스타트 온보딩 2문항(이용 목적 · 글씨 크기)으로 프리셋 카드 세트 배치 후, 5~10회 사용 시점부터 실측 랭킹으로 전환

06 — 알고리즘

점수는 서버가 아니라 기기 안에서 계산된다

랭킹 점수

score(m) = w_f · log(1 + freq(m)) 빈도 — 많이 쓴 것 + w_r · exp(-λ · Δt(m)) 최신성 — 최근에 쓴 것 + w_c · contextBoost(m) 상황 — 지금 쓸 법한 것 + w_p · isPinned(m) 고정 — 사용자가 박아둔 것
항기본값설계 의도
빈도w_f = 1.0로그를 씌워 다빈도 메뉴의 독점 방지 — 20번 쓴 메뉴가 20배 점수를 갖지 않게
최신성w_r = 0.6 · λ = 0.05/일반감기 약 14일. 최근 안 쓰면 서서히 내려간다
상황w_c = 0.4요일·일자 주기성과 시간대 일치. 매달 25일 관리비 이체 같은 패턴
고정w_p = 100사실상 무한대. 자동화가 실패할 때의 탈출구

히스테리시스 — 개인화에 브레이크 걸기

현재 카드 c를 도전자 d가 밀어내려면 두 조건을 모두 만족해야 한다 ① score(d) > score(c) × 1.20 20% 마진 ② 마지막 재배치로부터 24시간 경과 교체 확정 시 즉시 반영하지 않고 다음 앱 실행 시 반영 · 한 번에 최대 1장

세션 도중 화면이 바뀌는 일을 원천 차단하기 위한 구조다. 이 값들은 초기 가설이고, 사용자 테스트에서 조정 대상으로 명시해 뒀다.

왜 LLM API가 아닌가

LLM을 쓰면 “엄마한테 30만원”에서 수취인·금액까지 뽑을 수 있다. 그러나 발화가 외부로 나가면 금융권 망분리·개인정보 검토를 통과하기 어렵고, 왕복 지연이 1초를 넘으면 음성 UX가 무너지며, 호출 비용이 들고, 네트워크가 끊기면 기능이 죽는다. 포기한 것은 복잡한 문장의 파라미터 추출 능력이다. 대신 “메뉴를 찾아 화면까지 데려다주고, 값 입력은 화면에서 한다”로 범위를 좁혔다 — 07의 안전 설계와도 방향이 같다.

07 — 음성 설계

무료 STT로 검증하고, 유료 STT로 갈아 끼운다

interface SttProvider { start(): Promise<void>; stop(): void; onPartial(cb: (text: string) => void): void; onFinal(cb: (text: string, confidence: number) => void): void; onError(cb: (err: SttError) => void): void; }
단계구현체비용용도
개발·데모브라우저 Web Speech API0프로토타이핑, 시연
로컬 검증whisper.cpp 계열 로컬 모델0오프라인 동작, 인식률 비교
상용 전환상용 STT API유료실서비스 품질

교체 시 바뀌는 코드는 Provider 구현체 파일 하나다. 무료 STT의 낮은 인식률은 엔진 쪽에서 흡수한다 — 신뢰도 0.5 미만은 후보 없이 되묻기, 부분 인식 결과도 검색에 태워 체감 속도 확보, 1위만이 아니라 상위 3개 제시, 그리고 실패 문구는 열린 질문 대신 선택지 제시로: “이체, 조회, 내역 중에 찾으시는 게 있나요?”

안전 경계 — 음성은 어디까지 하는가

음성으로 가능

  • 메뉴 화면 열기
  • 최근 수취인 프리필
  • 조회성 기능 실행

음성으로 불가

  • 이체 실행
  • 금액 확정
  • 인증 통과
  • riskLevel: high 메뉴의 최종 확정

의도적으로 그은 선

잘못 인식된 송금은 되돌리기 어렵고, 음성만으로 자금이 이동하는 구조는 옆에서 시키는 대로 말하게 하는 공격에 취약하다. 주 사용자가 고령층인 만큼 이 리스크는 특히 무겁다. 이것은 기술적 한계가 아니라 판단이다 — “AI가 다 해준다”보다 “AI가 데려다주고 사람이 확인한다”가 금융에서 옳은 자동화 수준이다.

08 — 데모 은행 앱

엔진을 얹을 검증 베드를 직접 만든다

Spring Boot + JPA로 최소 계정계를 구현한다. 목표는 기능 개수가 아니라 금융 거래 처리의 정확성이다.

영역구현 내용
원장복식부기 — 이체 1건 = 출금 분개 + 입금 분개, 차변·대변 합 일치 검증
잔액컬럼 UPDATE가 아니라 원장 합계로 산출. 실제 계정계의 방식이고 정합성 감사가 가능하다
이체트랜잭션 경계 내 처리, 잔액 부족 검증, 실패 시 전체 롤백
멱등성요청별 Idempotency-Key로 네트워크 재시도에 의한 중복 이체 차단
동시성계좌 단위 락 + 재시도

프런트는 React로 만들되 같은 앱을 두 가지 UI로 전환 가능하게 한다 — 전형적인 메뉴 트리(약 25개)의 기본 UI 모드와, 엔진이 적용된 MinUI 모드. 두 모드는 동일한 백엔드와 동일한 기능을 쓰므로 UI 외의 변수가 통제된다. 카드에 올라오지 않는 21개 메뉴가 그대로 음성 탐색의 검증 대상이 된다.

09 — 검증 설계

측정 항목을 먼저 못 박아 둔다

지표정의목표
태스크 완료 시간“관리비 30만원 이체” 지시부터 완료까지−40%
탭 횟수동일 태스크 수행 중 화면 터치 횟수−50%
완료율도움 없이 태스크를 끝낸 참가자 비율≥ 90%
카드 적중률홈 카드만으로 목적을 달성한 세션 비율≥ 70%
음성 1회 성공률첫 발화로 올바른 메뉴에 도달한 비율≥ 75%
배치 안정성주당 카드 교체 횟수≤ 1
  • 모드 간 비교 측정 — 동일 참가자가 두 모드로 같은 태스크를 수행하고, 순서 효과를 없애기 위해 절반은 순서를 바꾼다. 시간·탭 수는 앱에 내장한 계측으로 자동 기록.
  • 사용자 테스트 — 60대 이상 5명, 40~50대 저빈도 사용자 3명. 발화 사고법으로 어디서 멈추는가, 어떤 단어로 기능을 부르는가(→ 동의어 사전에 반영), 카드가 바뀐 걸 알아채는가를 관찰.
  • STT 벤치마크 — 구어체 포함 50문장을 각 Provider에 태워 인식률·지연·검색 성공률 비교. 추상화의 실효성을 수치로 확인.

해석의 한계를 미리 적어 둔다

표본 8명은 통계적 검정력이 없다. 유의성을 주장하지 않고 관찰된 패턴과 개별 사례로 보고한다. 목표 수치도 가설이며, 실측 후 달성·미달을 그대로 기록하는 편이 더 가치 있다.

10 — 로드맵

단계마다 완료 기준을 숫자로 정의한다

M1
데모 은행 앱 — Spring Boot 계정계 + 기본 UI
이체 API가 복식부기로 기록되고, 멱등성 키로 중복 요청이 차단되며, 동시 이체 테스트를 통과한다
M2
core 랭킹 — EventStore · RankingEngine · 히스테리시스
이벤트를 주입하면 상위 N개가 산출되고, 20% 마진 미만 도전자는 교체를 일으키지 못한다 (단위 테스트)
M3
react 카드 UI — 디자인 토큰 · 접근성
데모 앱에서 모드 토글이 동작하고, 명도 대비·터치 타깃·스크린리더 검사를 통과한다
M4
검색 · 음성 — SearchPipeline · SttProvider
25개 메뉴에 대한 구어체 질의 50건 중 75% 이상이 1회 발화로 정확히 매칭된다
M5
측정 · 튜닝 — 계측 내장 · 사용자 테스트
09의 지표가 실측되고, 가중치·임계치가 결과에 근거해 조정된다

주요 리스크

리스크대응
개인화가 오히려 혼란을 준다 — 프로젝트 전제가 무너지는 리스크F3 배치 안정화 4종. 사용자 테스트의 최우선 검증 항목으로 지정
고령 발화에서 STT 인식률 급락흡수 장치 + 텍스트 검색을 항상 동등한 대안으로 제공. 음성은 보조 경로이지 유일 경로가 아님
메뉴 카탈로그 유지보수 부담앱 라우팅 테이블에서 카탈로그 초안을 생성하는 CLI, 검색 로그에서 동의어 후보 추출
온디바이스 임베딩 번들 크기벡터 데이터는 작고 인코더 모델 크기가 관건 — 경량 모델 선정과 실측을 M4 확인 항목으로 명시
데모 앱이 커져 엔진 개발이 밀림M1 범위를 이체·조회·원장으로 엄격히 제한. 상품 가입·대출은 메뉴만 두고 화면은 스텁

11 — 기술적 판단

이 프로젝트의 핵심은 기능 목록이 아니라 트레이드오프다

판단선택포기한 것이유
메뉴 탐색 AI온디바이스 임베딩 + 도메인 사전복잡한 문장의 파라미터 추출망분리 적합, 지연 없음, 비용 0, 오프라인 동작
개인화 방식온디바이스 규칙 기반협업 필터링의 콜드 스타트 이점사용 패턴의 외부 전송을 피하기 위해
반영 속도하루 1회 + 20% 마진최신 패턴 즉시 반영고령 사용자에게는 일관성 > 정확도
음성 실행 범위메뉴 호출 + 프리필까지“말만 하면 송금”의 데모 임팩트오인식·보이스피싱 리스크, 보안 심사 통과 가능성
패키지 구조core(무관) / react(바인딩) 분리단일 패키지의 단순함이식성이 이 프로젝트의 존재 이유
데모 잔액 처리원장 합계 산출조회 성능계정계 정합성 검증 가능성

확장 방향

  • 키오스크·ATM — 문제의 출발점이었던 곳. 다만 기기를 여러 사람이 공유하므로 사용 이력을 기기가 아니라 카드·계좌 인증 결과에 연결하고 세션 종료 시 폐기한다. StorageAdapter 교체만으로 대응 가능한 구조다.
  • 증권 앱 — 메뉴가 수백 개고 용어가 어려워(예수금, 미수, 반대매매) 동의어 사전의 가치가 더 커진다. 반면 시세처럼 실시간성이 중요한 화면은 카드화가 맞지 않아, 무엇을 카드로 올릴 수 있는가를 카탈로그 메타데이터로 표현하는 확장이 필요하다.
  • 보호자 원격 설정 — 처음 태블릿을 정리해 드릴 때처럼 가족이 카드를 고정해 드리는 기능. 타인이 금융 앱 화면을 바꾸는 일이므로 본인 동의와 권한 범위 제한이 전제다 — 조회성 설정만 허용하고 거래 관련은 제외한다.
