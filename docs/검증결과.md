# 검증 결과

## 지금까지의 요약 (2026-08-11)

한 화면에 담은 현재 상태다. 각 수치의 근거와 실패 기록은 아래 절들에 있다.

| | |
|---|---|
| 테스트 | 393개 통과 |
| 이식 대상 | 실제 금융사 5곳 (서비스 3 + cold data 2), 메뉴 2,948개 |
| 자동 수집 회수율 | **99%** (로그인 불필요 4곳) |
| 이식 시간 | 반나절 → **10초** (`/studio`) |
| 검색 — 온디바이스만 | 85% |
| 검색 — LLM 폴백까지 | **95%** |
| 답 없는 질의 100건 | 97건 옳게 거절 |
| 탭 감소 (미니은행) | 33% (목표 50% 미달) |

**이 수치들에 공통된 흠이 하나 있다.** 질의도 내가 쓰고 동의어도 내가 썼다 —
실제로 질의의 49%가 사람 동의어와 문자열로 겹치고 10건은 글자까지 같다.
그래서 <b>"LLM이 사람만큼 하는가"에는 아직 답할 수 없다.</b>
답하려면 둘 다 쓰지 않은 사람의 질의가 필요하고, 그것이 다음 할 일이다.

### 실패했고 되돌린 것들

같은 무게로 적어 둔다. 되돌린 이유가 다음 사람에게 더 쓸모 있다.

| 시도 | 결과 |
|---|---|
| 라벨 토큰으로 동의어 자동 생성 | 기여 0. 오히려 정확도 하락 |
| 용어 사전으로 라벨 부풀리기 | 기여 0, 색인 2배 |
| 용어 사전을 질의 쪽에 적용 | 77% → 75% **후퇴** |
| LLM 동의어를 색인에 넣기 | 85% → 67% **후퇴** |
| 위험도별 검색 임계값 | 후보 3개 포함 85% → 80% |
| `termSpecificityFloor` 조정 | 16칸 전부 같은 점수 (효과 0) |

공통점이 있다. **동의어를 미리 많이 붙일수록 서로를 방해한다.**
그 벽을 넘은 것은 미리 붙이기를 그만두고 <b>런타임에 사용자가 한 말을 보는</b> 쪽으로
옮긴 것이었다.

---

기획안이 가설로 적어 둔 수치를 실제로 재고, **달성/미달을 그대로** 남긴다.
목표를 맞추려고 기준을 옮기지 않는다.

## M4 — 메뉴 검색 (2026-08-10)

### 1회 발화 정확 매칭 — DoD 75%

| 지표 | 결과 |

| 되묻기 | 1/50 (2.0%) |
| 1순위를 올린 단계 | 정확 매칭 16 · 동의어 27 · 자모 보정 6 |

재현: `pnpm --filter tools bench:search`

> **이 수치를 그대로 믿으면 안 되는 이유.**
> 질의 세트를 내가 쓰고, 그 결과를 보고 카탈로그의 동의어를 보강했다. 기획안 §12.2-B가
> 의도한 피드백 루프("어떤 단어로 기능을 부르는가 → 동의어 사전에 반영")이긴 하지만,
> 같은 사람이 문제와 답을 함께 만든 셈이라 실사용 성능의 추정치가 아니다.
> 의미 있는 수치는 §12.2-B의 사용자 테스트에서 **처음 듣는 발화**로 다시 재야 나온다.
> 그때를 위해 이 세트는 고정해 두고 새 발화는 별도 파일로 쌓는다.

유일한 실패: `"주소 바꿔야 해"` → 되묻기.
`바꿔`와 사전의 `바꾸기` 사이 자모 유사도가 0.73으로 개입 하한(0.75)에 못 미쳤다.
하한을 낮추면 통과하지만 오탐이 늘어나므로 그대로 두었다. 활용형 처리는 M5의 조정 대상.

### 의미 매칭(n-gram TF-IDF)의 기여 — **0**

같은 세트를 의미 매칭을 켜고/끄고 돌렸을 때 결과가 **완전히 동일**했다.

| 구성 | 1회 발화 정확 매칭 |
|---|---|
| 동의어 + 자모 + n-gram | 49/50 |
| 동의어 + 자모만 | 49/50 |

기획안 §14가 M4의 확인 항목으로 남긴 질문("경량 임베딩 모델을 넣을 가치가 있는가")에
대한 이 단계의 답은 **아니오**다. 이유는 두 가지로 보인다.

1. 문자 n-gram이 잡는 것(어간 조각 겹침)은 동의어 사전과 자모 보정이 이미 덮는다.
2. 문자 n-gram이 못 잡는 것(`돈`↔`금액`처럼 글자가 겹치지 않는 동의 관계)은
   문장 임베딩 모델이라야 잡히는데, 그건 이 구현체의 한계가 아니라 방식의 한계다.

곧 "임베딩을 문장 모델로 바꾸면 나아질 여지"는 남아 있다. 다만 그 여지를 사려면
**색인 29.6 KB → 모델 100MB대**를 지불해야 한다. 기획안 §14가 번들 크기를 리스크로
꼽은 판단의 근거가 이 수치다.

| | 크기 |
|---|---|
| n-gram 색인 (메뉴 25개, n-gram 473개) | **29.6 KB** |
| 다국어 문장 임베딩 모델 (최소 규모) | 100MB대 |

재현: `pnpm --filter tools build:index`

`EmbeddingProvider` 인터페이스는 그대로 둔다. 지금 값을 못 한다는 것과
교체 지점이 필요 없다는 것은 다른 이야기이고, 증권 앱처럼 메뉴가 수백 개가 되면
판단이 달라질 수 있다.

## M1 — 데모 계정계 (2026-08-10)

### 통합 테스트 — 실제 PostgreSQL (Testcontainers)

| 검증 항목 | 결과 |
|---|---|
| 이체 후 전 계좌 차변 합 = 대변 합 | 통과 |
| 같은 멱등성 키로 동시 10건 → 이체 1건 | 통과 |
| 같은 계좌 쌍 양방향 동시 이체 20건 → 데드락·음수 잔액 없음 | 통과 |
| 잔액 부족 → 분개·이체·멱등성 기록 모두 롤백 | 통과 |
| 동시 출금 10건(각 30만원, 잔액 100만원) → 정확히 3건만 성공 | 통과 |
| 같은 키 + 다른 내용 → 409 거절 | 통과 |

재현: `docker compose -f backend/compose.yaml up -d && cd backend && ./gradlew test`

### HTTP 레벨 실측

같은 멱등성 키로 동시에 10건을 보냈을 때:

```
201 200 200 200 200 200 200 200 200 200
```

`201`(새로 처리) 하나에 `200`(이전 결과 재생) 아홉. 수취인 잔액은 한 번치만 늘었다.

전 계좌 잔액을 전(錢) 단위 정수로 합산한 결과 **정확히 0**. 자본 계정이 발행 총액의
음수를 들고 있고 나머지가 그 반대편에 있다 — 원장 밖에서 생긴 돈이 없다는 뜻이다.

### 이 단계에서 잡은 설계 오류 세 가지

1. **격리 수준을 REPEATABLE READ로 잡았던 것.** 직관과 반대로 이것이 틀렸다.
   PostgreSQL의 REPEATABLE READ는 트랜잭션 첫 문장에서 스냅샷을 고정하므로, 락을
   기다리던 두 번째 이체가 앞 트랜잭션이 방금 커밋한 출금 분개를 보지 못해 초과 인출이
   난다. READ COMMITTED로 바꿔야 락을 얻은 시점의 잔액이 보인다. 직렬화는 격리 수준이
   아니라 비관적 락이 맡는다.

2. **멱등성 검사를 락보다 먼저 한 것.** 같은 키의 두 요청이 나란히 "처음 보는 키"라고
   판단한 뒤 락 앞에 줄을 서면, 앞 요청이 커밋해도 뒤 요청은 그 사실을 모른다.
   실제로 동시 10건이 전부 이체를 만들어 냈다. 락을 먼저 잡으면 뒤 요청은 앞 요청이
   커밋한 뒤에야 검사에 도달한다.

3. **`save()`가 INSERT가 아니라 merge로 나간 것.** ID를 직접 할당하는 엔티티에
   Spring Data의 `save()`를 쓰면 "있으면 UPDATE"가 되어 기본 키 제약이 발동하지 않는다.
   중복 차단 장치가 있는데 조용히 덮어쓰고 있었다. `Persistable.isNew()`로 진짜
   INSERT가 나가게 했다.

세 가지 모두 **동시성 테스트가 없었으면 드러나지 않았을** 것들이다. 단위 테스트나
수동 클릭으로는 전부 정상으로 보인다.

## M5 — 계측과 개인화 측정 (2026-08-10)

재현: `pnpm vitest run --project frontend test/scenarios` → `pnpm --filter tools simulate`
→ `pnpm --filter tools report`

### 이 측정이 무엇이 아닌지 먼저

기획안 §12.2는 **사람 8명**(60대 이상 5, 40~50대 3)의 사용자 테스트를 설계해 두었다.
그것은 하지 않았다. 여기 있는 것은 **스크립트 자동 수행**이고, 스크립트는 망설이지 않고
헤매지 않고 글자를 읽는 데 시간을 쓰지 않는다.

그래서 §12.1의 1차 지표 네 개 중 **탭 횟수 하나만** 나온다. 나머지 셋(완료 시간, 완료율,
오탐색률)은 빈칸으로 둔다. 스크립트가 만든 숫자를 그 자리에 넣으면 표 전체가 거짓이 된다.

탭 횟수를 재는 것이 그래도 값어치 있는 이유는, 그것이 사람이 아니라 **UI 구조의 성질**이기
때문이다. "이 화면에서 이 일을 끝내려면 최소 몇 번 눌러야 하는가"는 사용자 테스트 없이도
지금 확정할 수 있다.

### 1차 지표 — 탭 횟수 (목표: 기본 UI 대비 50% 감소)

| 과제 | 쉬운 모드 | 기본 UI | 차이 |
|---|---|---|---|
| S1 반복 이체 | 3 | 3 | **0%** |
| S2 잔액 확인 | 0 | 0 | 동률 |
| 이체 한도 변경 | 2 | 3 | −33% |
| 인증서 관리 | 2 | 3 | −33% |
| 해외 송금 | 2 | 3 | −33% |

S3 자동이체 관리는 경로가 셋이라 따로 잰다.

| 경로 | 탭 |
|---|---|
| 쉬운 모드 · 전체 메뉴 | **3** |
| 쉬운 모드 · 음성 | 4 |
| 기본 UI · 메뉴 트리 | 4 |

**목표 50% 감소는 달성하지 못했다.** 최대 33%이고, 대표 시나리오 S1·S2에서는 차이가 0이다.

### 왜 0인가 — 기획안의 기준선 가정이 과했다

기획안 §5.2는 기존 UI의 이체를 **탭 5회**(홈 → 전체메뉴 → 이체 → 계좌이체 → 최근 목록 →
대상 선택)로 잡았다. 그런데 현대 은행 앱은 홈에 이체 바로가기와 계좌 잔액을 이미 올려 둔다.
대조군을 실제 앱처럼 만들었더니 S1은 3탭, S2는 0탭이었다 — 쉬운 모드와 같다.

이것은 MinUI가 못해서가 아니라 **기준선이 §5.2의 가정보다 좋기 때문**이다. 그리고 이 사실
자체가 기획안 §2.2의 주장과 일치한다: 실패는 *자주 쓰는 기능*이 아니라 *찾아야 하는 기능*에서
일어난다. 자주 쓰는 것은 어떤 앱이든 이미 홈에 있다.

차이가 나는 곳은 꼬리다 — 홈 바로가기에도 카드에도 없는 메뉴에서 일관되게 1탭(−33%)이
줄어든다. 쉬운 모드의 전체 메뉴가 25개를 한 목록에 펼치는 반면 기본 UI는 카테고리를 한 번
펼쳐야 하기 때문이다.

### 탭 횟수가 잴 수 없는 것

**탭 횟수는 난이도의 하한이고, 조밀한 UI에 유리하게 편향된다.** 기획안 §2.2가 말한 비용은
탭 자체가 아니라 매 단계의 "다음에 뭘 눌러야 하지"라는 판단이다. 배너와 8칸 아이콘 격자와
5개 탭바가 있는 홈에서 이체 버튼을 찾는 시각적 탐색 비용은 이 표에 한 글자도 반영되지 않는다.

음성 경로가 탭 수로는 4탭(기본 UI와 동률)인 것도 같은 이유다. 음성이 없애는 것은 탭이 아니라
**"자동이체 관리가 어느 카테고리에 있는지 알아야 하는 부담"**이다. 그것은 사람을 앉혀 놓고
재야 나온다.

### 2차 지표 — 카드 적중률과 배치 안정성

120일 사용 패턴 시뮬레이션. 목표는 적중률 70% 이상, 주당 교체 1회 이하.

| 페르소나 | 설정 | 카드 적중률 | 주당 교체 | 수렴 |
|---|---|---|---|---|
| A 김순자 (73세) | 기본 | **100.0%** | **0.00** | 변화 없음 |
| B 박현우 (46세) | 기본 (마진 20% · 1회 1장) | 50.0% | 0.29 | 61일 |
| B | 1회 2장 | 62.5% | 0.23 | 40일 |
| B | 마진 10% / 50% / 쿨다운 12h | 50.0% | 0.29 | 61일 |

**배치 안정성은 목표를 크게 넘겨 달성**했다(0.00~0.29 ≤ 1.0).
**카드 적중률은 페르소나에 따라 갈린다** — A는 100%, B는 50%로 목표 미달.

세 가지가 드러났다.

**1. 프리셋이 맞는 사용자에게 개인화는 아무것도 하지 않는다 — 그리고 그게 옳다.**
A는 120일 동안 카드가 한 번도 바뀌지 않았다. 안정화 장치가 "할 일이 없을 때 아무것도 하지
않는" 것이 원칙 P3의 실제 모습이다.

**2. 수렴이 느리다. 발목을 잡는 것은 파라미터가 아니라 세션 빈도다.**
B가 자리를 잡는 데 61일이 걸렸다. 마진을 10%로 낮춰도, 50%로 올려도, 쿨다운을 12시간으로
줄여도 **결과가 똑같았다**. B는 앱을 한 달에 네다섯 번 열고, 재배치는 세션당 한 번뿐이므로,
24시간 쿨다운은 애초에 걸리지도 않는다. 저빈도 사용자에게 부족한 것은 시간이 아니라 세션이다.

**3. 20% 마진은 프리셋→개인화 전환 구간에서 아무 일도 하지 않는다.**
프리셋 카드는 사용 기록이 없어 점수가 0이고, `0 × 1.2 = 0`이라 양수 점수를 가진 도전자는
마진과 무관하게 이긴다. 마진이 실제로 작동하는 곳은 양쪽 다 점수를 가진 **정상 상태의
재순위**뿐이다. 이것은 결함이 아니라 파라미터의 유효 범위이며, 기획안 §8.2를 읽을 때
그렇게 이해해야 한다.

### 파라미터를 바꾸지 않기로 했다

시뮬레이션은 `maxSwapsPerRecompute: 2`가 B에게 두 지표 모두에서 낫다고 말한다
(적중률 50%→62.5%, 주당 교체 0.29→0.23, 수렴 61일→40일). 교체를 빨리 끝내면 중간에
들락날락하는 카드가 줄어 총 교체 수까지 적어진다.

그럼에도 기본값을 1장으로 둔다. 이유는 두 가지다.

- 기획안 §8.2가 이 값의 조정 근거로 **사용자 테스트**를 지목했다. 카드가 하루 두 장 바뀌는
  것의 비용은 고령 사용자가 얼마나 혼란스러워하는가이고, 그것은 시뮬레이션이 매길 수 없는
  가격이다. 내가 만든 페르소나 두 명으로 P3에 직결된 값을 바꾸는 것은 근거를 넘어선다.
- 이 시뮬레이션의 사용 패턴은 내가 지어낸 것이다. 실제 사용 로그가 생기면 그것으로 다시
  재야 한다.

바꾸지 않았다는 사실과 그 이유를 남기는 것이, 수치가 좋아 보인다고 바꾸는 것보다 정확하다.

### id 불안정 문제와 그 해결 (2026-08-10 추가)

처음 기록한 한계는 이랬다 — 신한(1,004)과 미래에셋(370)은 사이트가 메뉴 코드를 주지 않아
id를 라벨 경로로 만들었고, 사이트가 문구를 바꾸면 id가 끊어지면서 손으로 붙인 동의어가
통째로 죽는다.

**먼저 로그인 상태에서 다시 확인했다.** 신한은행에 로그인하면 URL이
`bank.shinhan.com/index.jsp#011100000000`로 바뀌어 12자리 메뉴 코드가 보인다. 그런데:

- 전체메뉴 항목 수는 로그인 전후 **정확히 같은 1,004개** — 로그인으로 드러나는 메뉴는 없다
- 문서 전체에 12자리 코드가 **5개뿐** — 메뉴마다 붙어 있지 않다
- WebSquare DataList(`dl_R_mymenuSelect` 등)는 전부 비어 있다
- 앵커 속성은 `id`(불안정한 `wq_uuid_*`)·`class`·`href`(`javascript:void(null)`)뿐

즉 **사이트에서 안정적인 코드를 얻을 방법이 없다.** 코드는 클릭 시점에 동적으로 정해지고,
1,004개를 클릭해 알아내는 것은 로그인된 뱅킹 세션에 요청을 1,004번 던지는 일이라 하지 않았다.

#### 그래서 방향을 바꿨다 — 끊어져도 살아남게 만든다

`tools/src/overrides.ts`가 override를 네 단계로 붙인다.

1. **id 일치** — 코드가 있는 사이트(KB국민은행 `page`, KB증권 `linkcd`)는 여기서 끝난다
2. **`match.label`** — 작성자가 명시한 기준
3. **자모 유사도** — 문구가 조금 바뀐 경우. **엔진이 사용자 발화를 맞출 때 쓰는 그 함수**를
   그대로 재사용한다. 하한 0.82 미만이면 붙이지 않는다
4. 못 붙인 것은 **표류 리포트**로 남기고 가장 가까운 후보를 제시한다

#### 실제 수집 데이터로 개편을 재현했다

신한 원본에 문구 변경을 주입했다 — "자동이체 조회/변경/취소" → "조회·변경·해지",
"당행/다른기관이체" → "당행·타행 이체", 경로 "자동이체" → "자동이체관리".

```
id가 끊어져 다시 붙인 override 1건
  shinhan.개인-이체-자동이체-조회-변경-취소
    → shinhan.개인-이체-자동이체-조회-변경-해지  (자모 0.91)

붙지 못한 override 1건
  shinhan.개인-이체-당행-다른기관이체
    가장 가까운 메뉴: shinhan.개인-이체-당행-타행-지연이체-등록 (0.80)
```

첫 번째는 자동으로 복구됐다. **두 번째는 붙이길 거부한 것이 옳다** — 가장 가까운 후보가
"지연이체 등록"이라는 <b>다른 메뉴</b>였고, 여기에 "다른 은행으로 보내기" 동의어가 붙으면
사용자가 엉뚱한 화면으로 간다. 안 붙는 것보다 잘못 붙는 것이 나쁘다.

리포트 안내대로 `match: { label: "당행·타행 이체" }`를 넣자 고아 0건이 되고 14개 동의어가
모두 살아남았다. 재현은 `pnpm vitest run --project tools` (9개 테스트).

#### 남은 것

- **자동 재연결은 사람이 확인해야 한다.** 자모로 붙인 것은 전부 리포트에 남지만,
  리포트를 안 읽으면 잘못 붙은 채로 넘어간다. 하한 0.82는 이 세트에서 정한 값이라

#### 자모 재연결이 코드형 id에서 오작동했다

갈래가 사라지면서 그것을 가리키던 override 45건의 id가 끊어졌고, 자모 재연결이 전부

| 잃은 id | 붙은 곳 | 점수 |
|---|---|---|

| `C060833` 계좌이체 · "돈 보내기" | `C065633` **다른금융 계좌이체** | 0.86 |
| `C101318` 환율 · "달러 얼마" | `C101398` **웨스턴유니온송금** | 0.93 |

원인은 재연결이 라벨이 아니라 **id 문자열**을 비교한다는 것이었다. `C016513`과 `C016523`은
문자 93%가 같지만 뜻은 아무 관계가 없다. 라벨 기반 id(`shinhan.개인-이체-당행이체`)에는
성립하던 방식이 코드형 id에서는 성립하지 않는다.

**id에 한글이 있을 때만 자모 재연결을 시도하도록 고쳤다.** 코드가 사라졌다는 것은 사이트가
그 메뉴를 없앴거나 우리가 걸러냈다는 뜻이고, 그때 필요한 것은 추측이 아니라 사람의 확인이다.

두 번째 오류도 같이 잡았다. 세 단계(id 일치 → `match.label` → 자모)를 override 하나씩
통과시키고 있어서, 사라진 갈래 `shinhan.개인-조회`가 자모 1.00으로
`개인-조회-예금-신탁`을 먼저 차지하고 정작 그 id를 정확히 가진 override를 밀어냈다.
**단계별로 통과시키도록 바꿨다** — 확신이 있는 것이 전부 자리를 잡은 뒤에 추측이 시작된다.

### 카드 순서를 중요도 순으로 바꿨다 (2026-08-10 추가)

원래는 **자리를 지켰다**(§8.2) — 랭킹이 바뀌어도 남아 있는 카드는 움직이지 않고, 새 카드가
나간 카드의 자리에 들어갔다. 같은 자리에 같은 것이 있는 편이 고령 사용자에게 낫다는
판단이었다. 그것을 버리고 **위에서 아래로, 왼쪽에서 오른쪽으로 중요한 것부터** 놓는다.

순서는 점수 하나로 뭉뚱그리지 않고 단계로 정한다. 점수(빈도·최신성·상황의 합)로 정렬하면
"왜 이 카드가 위에 있는가"를 사용자에게 설명할 수 없기 때문이다.

1. **고정한 것이 먼저** — 사용자가 직접 정한 것이 자동 판단보다 위다
2. **조회 횟수가 많은 것부터** — 고정한 것끼리도 이 규칙을 먼저 적용한다
3. 횟수가 같으면 — 고정한 것은 **먼저 고정한 순서**, 아닌 것은 **최근에 본 순서**

2번이 3번보다 먼저인 것이 요점이다. 나중에 고정한 메뉴라도 더 많이 보면 앞으로 올라온다.

이를 위해 `ScoreBreakdown`에 `views`(원본 횟수)와 `lastUsedAt`을 실었다. 기존 `frequency`는
로그를 씌우고 미완료 방문에 0.25를 곱한 **점수**라 5회와 6회의 차이가 0.15밖에 안 되고,
최신성 항이 그것을 뒤집는다 — 사용자가 보기에는 덜 쓴 메뉴가 위에 있는 상태가 된다.

실측(하나은행 데모, 초기화 상태): `자동이체 조회/변경/취소`를 6번, `계좌이체`를 3번 열자
카드가 `자동이체(6) → 계좌이체(3) → 계좌조회(0) → 거래내역조회(0)` 순이 됐다. 그 뒤
`거래내역조회`(0회)를 고정하자 6회짜리를 제치고 1행 1열로 올라왔다.

`packages/core/test/MinUIEngine.test.ts`에 7건, 언어 중립 픽스처 2개도 함께 고쳤다.
**카드 구성이 바뀌는 규칙(마진 20% · 쿨다운 · 1회 1장)은 건드리지 않았다** — 바뀐 것은
같은 넉 장을 어떤 순서로 놓느냐다.

어느 쪽이 나은지는 사용자 테스트로만 답할 수 있고, 아직 하지 않았다.

정답 메뉴가 실제로 몇 점을 받았는지 봤다. 채점 로직을 다시 구현하지 않은 것이 요점이다 —
그러면 재는 대상과 재는 자가 달라진다.

#### 결과 — 예상이 틀렸다

| 실제 상태 | 건수 | 뜻 |
|---|---|---|
| **정답이 이미 1위인데 문턱(0.55)에 걸림** | 7 | 랭킹은 맞혔다. 확신이 모자랐을 뿐이다 |
| 정답이 2~3위 — 화면에 후보로 이미 보임 | 7 | 그중 **3건은 갈래와 정확히 동점** |
| 정답이 2~3위인데 문턱에 걸림 | 2 | |
| 정답이 4위 밖 | 2 | 랭킹이 진짜로 틀렸다 |
| 정답이 0점 | 1 | 질의의 말이 어디에도 없다 |

**"되묻기 10건은 정보가 없어서"라고 적었던 것이 틀렸다.** 10건 중 7건은 정답이 이미
1위였고, 점수만 0.219~0.466으로 낮았다. 즉 이 구간의 실패는 검색의 실패가 아니라
**임계값의 실패**다.

```
되묻기  "빌린 돈 내역"        정답 대출계좌조회      0.466 semantic 1위
되묻기  "찾을 수 있는 금액"    정답 출금가능금액조회   0.420 semantic 1위
되묻기  "매달 빠져나가는 거"   정답 자동이체내역...   0.395 semantic 1위
되묻기  "계좌 새로 만들래"     정답 온라인 계좌개설    0.323 semantic 1위
되묻기  "급여 자동으로 들어오게" 정답 급여이체 서비스   0.279 semantic 1위
되묻기  "다른 은행으로 부쳐야 해" 정답 당행/다른기관이체 0.219 semantic 1위
```

M4에서 "n-gram 의미 매칭의 기여는 0"이라고 적었는데, 그 측정과 이것은 어긋나지 않는다.
n-gram은 **순서는 맞히지만 절대 점수가 낮다.** 임계값이 0.55라 그 순서가 화면에
도달하지 못했을 뿐이다. 기여가 0으로 보였던 이유가 여기 있다.

#### 갈래 문제의 절반은 동점 문제였다

| 질의 | 1위 | 정답 | 점수 |
|---|---|---|---|
| "환율 알려줘" | 환율 | 환율조회 | **0.810 = 0.810** |
| "펀드 뭐 있어" | 펀드 | 펀드몰 | **0.810 = 0.810** |
| "펀드 알아보고 싶어" | 펀드 | 펀드검색 | **0.765 = 0.765** |

동의어가 갈래와 자식에 똑같이 걸려 점수가 같고, 동점은 카탈로그 순서로 깨진다.
수집 원본이 DOM 순서라 갈래가 항상 앞이다. **"자식이 있는 항목은 동점일 때 뒤로"라는
규칙 한 줄로 세 건이 뒤집힌다** — 점수 체계를 건드리지 않고.

나머지 한 건은 진짜 손실이다. "청약 넣으려고"에서 갈래 `청약`이 semantic **1.000**을 받고
정답 `공모주청약`은 0.237로 7위였다. 두 글자짜리 짧은 라벨이 n-gram에서 만점을 받는
치우침이다.

#### 이 측정으로도 답할 수 없는 것

임계값을 내리면 몇 건이 살아나는지는 계산할 수 있다.

| 임계값 | 살아나는 건수 | 1회 질의 정확 매칭 |
|---|---|---|
| 0.55 (현재) | — | 68% |
| 0.40 | +2 | 72% |
| 0.30 | +5 | 77% |
| 0.20 | +7 | 80% |

**하지만 이 숫자는 반쪽이다.** 질의 60문항이 전부 정답이 있는 문항이라, 임계값을 내렸을 때
*되물었어야 할 질의*가 얼마나 잘못된 확신으로 바뀌는지는 이 세트로 잴 수 없다.
"날씨 어때" 같은 답이 없어야 하는 문항이 세트에 하나도 없다.

**임계값을 만지기 전에 답 없는 질의 세트를 먼저 만들어야 한다.** 그것 없이 0.55를 0.30으로
내리면, 정확도가 77%로 오른 것처럼 보이면서 실제로는 아무 말에나 자신 있게 엉뚱한 메뉴를
들이미는 상태가 된다. 위험이 무제한은 아니다 — `riskLevel: high`는 자동 실행되지 않고
`autoOpenConfidence`(0.9)도 그대로다. 바뀌는 것은 "되묻기 → 후보 3개 제시"까지다.

### 정확도 작업 — 무엇이 듣고 무엇이 안 들었나 (2026-08-10 추가)

0번 측정 결과를 근거로 순서대로 손봤다. **두 가지는 들었고 한 가지는 실패했다.**

| 손댄 것 | 1순위 정답 | 성격 |
|---|---|---|
| 시작 | 68% | |
| ① 동점이면 자식이 갈래를 이긴다 | **73%** | 규칙 한 줄 |
| ② 정확 매칭이 semantic으로 분류되던 버그 | 73% | 결함 수정 |
| ③ 임계값 0.55 → 0.40 | **77%** | 저울을 보고 고른 값 |
| ④ 용어 사전을 질의 쪽에 적용 | 75% (**후퇴**) | 채택 안 함 |
| ⑤ 동의어 확장 (서비스 3곳) | 82% | **자기 채점** |

#### ① 동점 규칙 — 예측대로 3건

동의어는 갈래와 자식에 똑같이 걸린다. `환율`(갈래)과 `환율조회`가 0.810으로 정확히 같고,
동점은 카탈로그 순서로 깨지는데 수집 원본이 DOM 순서라 갈래가 언제나 앞이었다.
`MenuIndex`가 `hasChildren`을 계산하고, `SearchPipeline`이 **동점일 때만** 자식을 앞세운다.

갈래를 감점하지 않은 이유는 갈래가 진짜 목적지인 경우가 실재하기 때문이다
(KB국민은행 `계좌이체` 아래에는 평범한 이체 화면이 없다). 점수로 눌러 두면 그런 메뉴가
영영 안 나온다. 동점일 때만 양보시키는 것이 근거에 맞는 크기다.

#### ② 정확 매칭이 사라지던 버그

동점 규칙을 테스트로 굳히다가 드러났다. `#scoreMenu`의 `consider()`가 **먼저 계산된 쪽**을
남기는데 계산 순서상 의미 유사도가 맨 앞이었다. 라벨이 질의와 완전히 같으면 n-gram 유사도도
1.000이라, 정확 매칭(1.000)이 `1 > 1`을 통과하지 못하고 그 메뉴가 `semantic`으로 분류됐다.
바로 다음 줄에서 "정확 매칭이 있으면 정확 매칭만 남긴다"는 필터가 도는데,
**가장 정확한 그 메뉴가 후보에서 통째로 빠졌다.**

"환율"을 찾으면 `환율`이 사라지고, "청약"에서는 갈래 `청약`이 semantic 1.000으로 1위를
차지했다. 점수는 맞고 <b>분류가 틀린</b> 것이라 점수만 보는 벤치마크로는 잡히지 않았다.
같은 점수면 근거가 강한 단계를 남기도록 고쳤다(exact > synonym > phonetic > semantic).

#### ③ 임계값 — 저울을 만들고 나서 고쳤다

답이 있는 질의만으로 재면 임계값은 내릴수록 좋아 보인다. 얻는 쪽만 세기 때문이다.
그래서 **답이 없어야 하는 질의 20문항**을 먼저 썼다("날씨 어때", "택시 불러줘",
"손자 생일이 언제였지"). 되묻는 것이 정답인 문항이다. 사이트와 무관하므로 네 곳에 모두 돌려
80문항이 된다.

재현: `pnpm --filter tools tune:threshold`

| 임계값 | 1순위 정답 | 후보 3개 안 | 옳게 되물음 | 잘못된 확신 |
|---|---|---|---|---|
| 0.55 | 73% | 80% | 100% | 0건 |
| 0.45 | 75% | 82% | 96% | 3건 |
| **0.40** | **77%** | **85%** | **94%** | **5건** |
| 0.35 | 78% | 87% | 90% | 8건 |
| 0.30 | 82% | 92% | 85% | 12건 |
| 0.20 | 85% | 95% | 74% | 21건 |

0.40을 골랐다. 0.30이 정확도는 더 높지만 답 없는 질의의 15%에 엉뚱한 메뉴를 자신 있게
내민다. **무릎이라고 본 것이지 계산 결과가 아니다.**

안전 경계는 이 값과 무관하다. 자동 실행은 `autoOpenConfidence`(0.9) · 단일 후보 ·
`riskLevel != high`를 모두 요구하므로, 이 값이 바꾸는 것은 "되묻기 → 후보 3개 제시"까지다.

**위험도별 임계값은 재 보고 버렸다.** 일반 메뉴만 0.40으로 내리고 `riskLevel: high`는
0.55로 두면 잘못된 확신이 5건 → 4건으로 줄지만, 후보 3개 포함이 85% → 80%로 떨어진다.
정답인 high 위험 메뉴가 후보에서 함께 잘려 나가기 때문이다. 손해가 이득보다 컸다.

#### ④ 용어 사전, 이번엔 질의 쪽 — 또 실패했다

전에는 사전으로 **라벨을 부풀렸고** 기여가 0이었다. 이번에는 반대 방향을 시도했다 —
사용자의 말을 사이트의 말로 바꿔서("돈 빼려고" + 출금) 한 번 더 찾고 메뉴별 최고점을 취한다.
색인은 그대로고 질의만 몇 갈래로 늘어난다.

재현: `pnpm --filter tools bench:expand`

**77% → 75%로 후퇴했다.** 얻은 것 1건, 잃은 것 2건.

```
얻음  "수익 났나 보자"    → 기준가/수익률조회
잃음  "계좌 확인서 필요해" → 1위가 증명서(갈래)로 바뀜
잃음  "빠르게 송금"       → 1위가 이체(갈래)로 바뀜
```

**이유를 이제 말할 수 있다.** 구어를 사이트 용어로 바꾸면 질의가 <b>더 일반적</b>이 된다.
"계좌 확인서"는 특정 화면을 가리키지만 "증명서"는 갈래를 가리킨다. 일반적인 말은 일반적인
메뉴에 걸린다. 라벨 쪽 적용이 실패한 것과 같은 벽이며, 방향을 뒤집어도 넘지 못했다.

코어를 고치기 전에 도구에서 흉내만 내 재 봤다. 그래서 실패한 실험이 코드로 남지 않았다.

#### ⑤ 동의어 확장 — 숫자는 믿지 마라

신한 17 → 23개, KB증권 26 → 30개, 하나 22 → 26개 메뉴에 구어를 붙였다.
서비스 세 곳의 점수는 신한 73 → 80%, KB증권 80 → 93%가 됐다.

**이 숫자를 정확도라고 부르면 안 된다.** 동의어를 붙일 때 나는 <b>어느 질의가 실패했는지
이미 보고 있었다.</b> 신한 `개인-조회-대출`에는 질의 문장("빚 얼마 남았어")을 글자 그대로
동의어로 넣었다. 문제를 보고 답을 쓴 것이다.

동의어를 지우지 않은 이유는 그것이 <b>제품으로는 옳기</b> 때문이다. 실제 사용자도 "빚 얼마
남았어"라고 말할 것이다. 다만 그렇게 만든 82%는 실사용 추정치가 아니라 상한선이며,
`tools/fixtures/site-queries.json`에 그 사실을 적어 뒀다.

**다음 측정은 다른 사람이 쓴 문항으로 해야 한다.** 그 전까지 이 프로젝트가 정직하게 말할 수
있는 숫자는 ①②③까지의 **77%**다.

#### 남은 실패 11건

| 원인 | 건수 | 예 |
|---|---|---|
| 정답이 2~3위 — 화면에는 보임 | 6 | "이체 한도 늘려줘" 1위=계좌이체 |
| 되묻기 (전부 0.40 미만) | 4 | "돈 빼려고" 정답 0점 |
| 갈래가 이김 | 1 | "청약 넣으려고" → `청약` semantic 1.000 |

마지막 건은 **짧은 라벨의 n-gram 치우침**이다. 두 글자 라벨은 질의에 그 두 글자가 들어 있기만
하면 코사인 유사도 1.000을 받는다. 동점이 아니라서 ①의 규칙이 닿지 않는다.
`semanticWeight`를 낮추면 잡히지만, 되묻기를 살려 낸 0.22~0.47 구간도 함께 내려앉는다 —
같은 항이 한쪽에서는 약이고 한쪽에서는 독이다. 재 보지 않고 만질 값이 아니다.

### 파라미터를 튜닝 세트와 검증 세트로 나눠 골랐다 (2026-08-11 추가)

지금까지의 모든 수치에는 같은 흠이 있었다. 질의도 내가 쓰고 동의어도 내가 붙였고,
나중에는 <b>어느 질의가 실패했는지 보고 나서</b> 동의어를 붙였다.

그런데 나눌 수 있게 됐다. 실패를 보고 동의어를 고친 곳은 **신한·KB증권·하나 셋뿐**이고,
KB국민·미래에셋은 서비스 대상에서 빠지면서 손대지 않았다. 그래서 이렇게 했다.

- **튜닝 세트** — 신한·KB증권·하나 (45문항 + 답 없는 60문항). 여기서 파라미터를 고른다
- **검증 세트** — KB국민·미래에셋 (30문항 + 답 없는 40문항). **고른 뒤 한 번만 본다**

재현: `pnpm --filter tools tune:search`

#### 잰 것 — `semanticWeight` × `termSpecificityFloor`

`termSpecificityFloor`는 이번에 설정으로 꺼냈다. 짧은 표현이 긴 질의에 걸렸을 때 남겨 줄
점수의 바닥으로, `SearchPipeline` 안에 `0.8`로 박혀 있던 값이다. config.ts가 "튜닝 가능한
값은 전부 여기 모인다"고 해 놓고 이것만 코드에 있었다.

**결과: floor는 아무것도 바꾸지 않았다.** 0.80 · 0.65 · 0.50 · 0.35 네 값이 16칸 전부에서
같은 점수를 냈다. `계좌이체`의 동의어 "이체"가 "이체 한도 늘려줘"에 걸리는 문제를 잡으려던
것인데, 0.35까지 내려도 0.48로 정답의 0.446을 여전히 이긴다. 설정은 남겼다 — 값이
코드에 박혀 있던 것 자체가 config.ts의 규칙 위반이었고, 0을 잰 것도 기록이다.

`semanticWeight`는 달랐다.

| semantic | 튜닝 1순위 | 튜닝 되물음 | 합 |
|---|---|---|---|
| **0.85** | 89% | **98%** | **1.872** |
| 0.70 | 87% | 100% | 1.867 |
| 1.00 (전) | 91% | 90% | 1.811 |

#### 검증 세트에서도 올랐다 — 다만 1건이다

| | 1순위 | 후보 3개 안 | 옳게 되물음 |
|---|---|---|---|
| 지금 값 (1.00) | 23/30 77% | 87% | 100% |
| 고른 값 (0.85) | **24/30 80%** | 87% | 100% |

뒤집힌 한 건이 진단과 정확히 같은 패턴이었다.

```
"자동이체 그만하고 싶어"
  1.00 → 자동이체 (갈래, semantic 0.837)
  0.85 → 자동이체내역 조회/해지/변경 (synonym 0.792)   ← 정답
```

n-gram은 이 파이프라인에서 **가장 약한 근거인데 가장 큰 점수를 낼 수 있는** 항이다.
짧은 라벨은 질의에 그 글자가 들어 있기만 하면 코사인 1.000을 받는다. 사람이 붙인 동의어보다
통계가 앞서는 것은 §8.3이 정한 단계 순서와 어긋난다.

**효과 크기는 정직하게 적는다 — 30문항 중 1건이다.** 이 수치 자체를 근거로 삼기는 어렵다.
채택한 이유는 방향이 진단과 맞고 <b>잃는 것이 없었기</b> 때문이다(후보 3개 포함과 되묻기 모두 그대로).

#### 뜻밖의 소득 — 잘못된 확신이 5건에서 1건으로

임계값 저울을 다시 재니 왼쪽 열이 통째로 좋아졌다.

| 임계값 | 1순위 | 옳게 되물음 | 잘못된 확신 (전) | (후) |
|---|---|---|---|---|
| 0.40 (현재) | 82% | **99%** | 5건 | **1건** |
| 0.35 | 83% | 95% | 8건 | 4건 |
| 0.30 | 85% | 90% | 12건 | 8건 |

답 없는 질의에 엉뚱한 메뉴를 내밀던 것이 전부 semantic 매칭이었기 때문이다.
**임계값은 0.40 그대로 두었다.** 무릎이 옮겨 간 것처럼 보이지만, 이미 여러 번 들여다본
데이터로 같은 값을 다시 고르는 것은 과적합이다. 0.35의 선택지가 있다는 사실만 남긴다.

#### 대가 — 미니은행 벤치가 100% → 98%

`"주소 바꿔야 해"` 한 건이 semantic 점수가 낮아지며 다시 되묻기로 돌아갔다.
50문항 중 1건이고 DoD(75%)에는 여유가 있지만, 공짜가 아니었다는 사실은 적어 둔다.

#### 검증 세트는 이제 썼다

이 결정에 검증 세트를 썼으므로 **다음 튜닝에는 쓸 수 없다.** 파라미터를 또 만지려면
새 세트가 필요하고, 그때는 질의를 다른 사람이 써야 한다.

### 자동 수집기 — `services/harvester`

URL 하나를 넣으면 Playwright가 전체메뉴를 열고 계층을 읽어 `raw.json`을 만든다.
출력 형식은 손 수집본과 글자 하나 다르지 않다 — 그래야 `build-catalog.ts`의 검증
(개인정보 필터·id 규칙)이 그대로 돌고, 손 수집본과 대조할 수 있다.

재현: `pnpm --filter @minui/harvester harvest -- <URL> [이름]` · `… recall`

"덤"(손 수집이 놓쳤거나 자동이 잘못 담은 것)을 여기서 구분하지 않았다. 구분하려면 사람이
목록을 봐야 하고, 그것을 자동으로 정하면 측정이 자기 채점이 된다.

#### 두 번의 실패로 배운 것

처음 돌렸을 때 5곳 중 3곳이 **깊이 0단만** 수집됐다(신한 99 · 미래에셋 73 · KB국민 67).
원인이 둘이었고, 둘 다 추측으로는 못 찾았을 것이다 — DOM을 직접 재고 나서야 보였다.

**① 신한은행에서 "전체메뉴 닫기"를 눌렀다.** 트리거를 이름으로 골랐더니 닫기 버튼이
먼저 걸렸고, 열려 있던 패널을 접어 버렸다. 1,004개짜리 메뉴가 99개가 됐다.
→ 여는 것과 닫는 것은 **결과로만 구별된다.** 누른 뒤 링크 수가 늘었는지 확인하고,
안 늘면 다음 후보로 넘어간다. 신한이 219 → 1,251로 늘었다.

**② 뿌리를 "링크 20개 넘으면 확정"으로 골랐다.** 머리글의 얕은 목록이 먼저 걸려
하위 메뉴를 통째로 놓쳤다. → 후보를 전부 훑고 **링크 수 × 계층 깊이**가 가장 큰 그릇을
고른다. 계층이 있는 그릇이 곧 메뉴 트리다.

**③ 프레임 안에서 트리거를 누르니 실행 컨텍스트가 날아갔다.** 미래에셋이 프레임셋인데,
클릭이 프레임을 갈아치우면서 그 뒤의 추출이 통째로 실패해 415개짜리에서 0개를 가져왔다.
→ **먼저 읽고 나중에 누른다.** 누른 뒤에는 프레임을 URL로 다시 찾는다. 0 → 455개.

#### 다듬으면서 세 가지가 더 나왔다 (2026-08-11 추가)

**① 회수율 측정이 틀린 것을 재고 있었다.** KB증권이 89%로 나왔는데, 놓쳤다는 76건 중
대부분이 `"펀드몰 하위메뉴"` 같은 스크린리더용 문구였다. 빌더가 어차피 지우므로 카탈로그에는
애초에 없다 — <b>자동 수집이 실제보다 나빠 보였던 것</b>이고, 손 수집이 담은 쓰레기였다.
정리 규칙을 `tools/src/labels.ts`로 빼내 빌더와 측정이 같은 것을 쓰게 하니
KB증권 89% → **98%**, 전체 97% → **99%**가 됐다.

**② 웹서비스로 띄우기 전에 필요한 것을 넣었다.** 사용자가 준 URL로 서버가 접속하는 구조라
`http://169.254.169.254`를 넣으면 서버가 자기 클라우드 자격증명을 대신 긁어다 준다.
사설 대역·내부 이름·`file:` 스킴을 막고, `robots.txt`를 읽어 막힌 경로는 수집하지 않는다
(`services/harvester/src/guard.ts`, 테스트 12개). **다만 이 함수만으로 안전하지 않다** —
도메인이 사설 IP로 풀리는 경우(DNS 리바인딩)는 나가는 요청 자체를 막아야 한다.
코드에 그 사실을 적어 뒀다.

**③ 은행 페이지가 `JSON.stringify`를 망가뜨린다.** 하나은행은 `Array.prototype.toJSON`을
정의해 두는데, 그러면 `{a:[1,2]}`가 `{"a":"[1, 2]"}`로 직렬화된다. **배열이 문자열이 된다.**
그 상태로 내려받은 파일은 `items`가 배열이 아니라 문자열이라, 그다음 단계가 전부 조용히
어긋난다. 실제로 그런 파일을 한 번 만들어 냈다.

이것은 이 프로젝트에서 두 번째로 만난 같은 현상이다 — 처음 하나은행을 손으로 수집할 때도
`items`가 문자열로 나왔고, 그때는 브라우저 확장의 문제로 생각하고 Node에서 다시 파싱해
넘어갔다. **원인이 페이지 쪽에 있었다.** 남의 페이지에서 도는 코드는 표준 함수조차
자기 것이 아니라고 봐야 한다. 직렬화하는 동안만 `toJSON`을 떼어 두고 되돌려 놓는다.

### 로그인 뒤 메뉴 — 브라우저 스니펫

서버 수집이 못 하는 일이 하나 있고(KB국민은행 3%), 그것이 은행 입장에서는 본체다.
같은 추출 로직을 esbuild로 9.8KB IIFE로 묶어 **사용자가 자기 브라우저 콘솔에 붙여넣는**
경로를 만들었다. 로그인한 그 화면에서 돌므로 서버가 못 보는 것을 보고,
<b>수집물이 서버를 거치지 않고</b> 곧장 사용자 컴퓨터로 내려간다.

추출·id 규칙은 서버 수집과 **같은 파일**을 쓴다. 따로 두면 한쪽만 고쳐져 두 경로가 다른
카탈로그를 만든다. 그래서 묶인 스니펫을 실제 페이지에 넣고 서버 수집과 대조한다
(`pnpm --filter @minui/harvester verify:snippet`).

| 사이트 | 서버 수집 | 스니펫 | |
|---|---|---|---|
| 하나은행 | 786 | **786** | 일치 |
| 신한은행 | 1,156 | **1,156** | 일치 |
| KB증권 | 1,443 | **1,443** | 일치 |

검사를 만들면서도 두 번 헛짚었다. `<script>` 태그 주입은 **은행 CSP가 막는다**(콘솔
붙여넣기는 막히지 않는다 — `evaluate`가 같은 통로다). 그리고 결과를 `window`에 얹어 두고
읽었더니 페이지가 도중에 다시 뜨면서 사라졌다 — 스니펫은 786개를 제대로 모으고 콘솔에
찍기까지 했는데 검사는 "결과 없음"이었다. **곁길로 확인하면 그런 일이 난다.**
사용자가 실제로 손에 넣는 것은 파일이므로 파일을 본다.

#### id 안정성

`services/harvester/src/keys.ts`가 링크에서 id를 뽑는다. 다섯 사이트를 손으로 수집하며
확인한 것은 코드가 **저마다 다른 자리**에 있다는 것이다.

```
KB국민은행   ?page=C016536         쿼리 파라미터
KB증권       ?linkcd=m02010002     쿼리 파라미터 (이름이 다르다)
하나은행     onclick="…102689"     onclick 안의 숫자
신한·미래에셋  javascript:void(null)  아무것도 없다 → 라벨 경로
```

그래서 한 규칙이 아니라 **안정성 순 사다리**다(쿼리 코드 → onclick 숫자 → 요소 id →
pathname → 라벨 경로). 라벨 경로는 사이트가 문구를 바꾸면 끊어지므로 마지막이다.
`services/harvester/test/keys.test.ts`의 17개 테스트는 전부 실제 사이트에서 본 모양이다 —
지어낸 예로 재면 수집기가 현실에서 무엇을 만나는지 알 수 없다.

미래에셋의 코드 id 비율이 2%인 것은 그 사이트가 코드를 아예 주지 않기 때문이다.
그 카탈로그는 사이트 개편에 취약하며, 그것이 override 재연결 장치를 만든 이유다.

### LLM 보강기 — 그리고 실험이 성립하지 않는다는 발견 (2026-08-11)

`services/enricher`가 Gemini 3.1 Flash Lite로 메뉴마다 네 가지를 만든다 — 구어 호칭,
위험도, 카드 가능 여부, 한 줄 뜻풀이. 산출물은 `*.ai.json`이고 빌더가
`raw < ai < 사람` 순으로 합친다. **사람이 쓴 것은 언제나 이긴다.**

재현: `pnpm --filter @minui/enricher enrich -- <사이트>` · `pnpm --filter tools bench:sites`

| | 사람이 붙인 것 | LLM이 붙인 것 |
|---|---|---|
| 동의어가 있는 메뉴 | 121 / 2,948 | **2,948 / 2,948** |
| 뜻풀이 | 0 | **2,306** |
| 위험도 판정 | 정규식 | 정규식 + 모델(더 위험한 쪽) |

무료 한도로 전부 처리됐고 **재시도 0건**이었다. 메뉴당 약 100토큰(입출력 합)이므로
5개 사이트 전체 재생성이 30만 토큰 규모다. 사이트당 1회이고 사용자 수와 무관하다.

#### 결과 — LLM 동의어는 사람 것의 1/3이다

| 구성 | 전체 5곳 | 손대지 않은 2곳 |
|---|---|---|
| A 라벨만 | 4% | 7% |
| B 사람 | **85%** | **80%** |
| C LLM | 31% | 30% |
| D 사람+LLM | 67% | 63% |
| E LLM(사람과 같은 범위) | 37% | 33% |

두 가지가 눈에 띈다.

**D가 B보다 낮다(85% → 67%).** 사람 것에 LLM 것을 더했더니 <b>떨어졌다.</b>
사람이 손대지 않은 2,800개 메뉴에 동의어가 붙으면서 정답을 밀어냈다.
M4에서 라벨 토큰을 자동 생성했을 때와 같은 현상이며, **동의어는 많을수록 좋은 것이 아니다.**

**E가 C보다 6점밖에 높지 않다(31% → 37%).** 사람과 똑같이 121개에만 붙여도 B의 절반이
안 된다. 그러니 간섭이 주원인이 아니라 **품질 차이**로 보인다.

#### 그런데 이 비교는 성립하지 않는다

여기서 멈추고 "LLM은 사람의 1/3"이라고 적을 뻔했다. 그 전에 한 가지를 셌다.

```
질의 75건 중
  사람 동의어와 글자까지 같은 것        10건
  사람 동의어에 포함되거나 포함하는 것   37건 (49%)
```

`"빚 얼마 남았어"` `"얼마 벌었어"` `"뺄 수 있는 돈"` `"나중에 보내기"` — **질의와 동의어가
글자까지 같다.** 질의도 내가 쓰고 동의어도 내가 썼으니 당연한 결과다.

**그러므로 B의 85%는 "사람이 잘 썼다"가 아니라 "질의를 쓴 사람이 답도 썼다"를 재고 있다.**
LLM은 질의를 보지 못했으므로 그 이점이 없다. 이것은 품질 차이가 아니라 <b>출제자와
답안자가 같은가</b>의 차이이고, 그 상태에서 B와 C를 나란히 놓는 것은 잘못이다.

앞서 "LLM 동의어는 구조적으로 깨끗하다"고 적었는데, **깨끗한 쪽이 불리한 구도였다.**
오염을 없앤 것이 아니라 한쪽에만 남겨 둔 것이다.

#### 그래서 지금 말할 수 있는 것과 없는 것

**말할 수 있는 것**
- LLM은 2,948개 <b>전부</b>에 동의어를 붙였다. 사람은 121개였고, 나머지를 채우려면
  사이트당 반나절이 더 든다
- 뜻풀이 2,306개는 사람이 하나도 만들지 않은 것이다(§15가 지목한 증권 용어 장벽)
- 무료 한도로 끝났고 사이트당 1회다
- **동의어를 전 메뉴에 붙이면 오히려 정확도가 떨어진다**(D < B). 이건 오염과 무관한 결과다

**말할 수 없는 것**
- "LLM이 사람만큼 한다" 또는 "LLM이 사람보다 못하다" — <b>이 세트로는 답이 안 나온다</b>

답하려면 **질의를 쓴 사람도, 동의어를 쓴 사람도 아닌 제3자의 질의**가 필요하다.
가족 사용자 테스트(§12.2-B)가 정확히 그 자리다. 그때 나온 말로 다시 재는 것이
이 프로젝트에서 처음으로 공정한 비교가 된다.

#### 만들면서 고친 것들

**① `cardable: false`가 93%였다.** 모델이 "별로 안 쓸 것 같다"는 이유로 카드에서 뺐다.
그러면 그 사람에게 꼭 필요한 메뉴가 영영 홈에 못 올라온다 — **무엇을 자주 쓰는지는
사용 기록이 정할 일**이지 모델이 미리 막을 일이 아니다. 프롬프트를 "내용이 계속 바뀌어
고정이 무의미한 화면"으로 좁히니 93% → 0~15%가 됐다.

**② 위험도가 65%였다.** `해지계좌 조회`처럼 <b>읽기만 하는 화면</b>이 `해지`라는 글자
때문에 high가 됐다. high가 65%면 음성이 "언제나 확인 한 번 더"가 되어 주 기능이 무너진다.
규칙을 `tools/src/risk.ts`로 빼내고 **라벨이 조회·내역·현황으로 끝나면 읽는 화면**으로
고쳤다 — 한국어 금융 메뉴는 마지막 명사가 그 화면이 하는 일이다. 65% → 40%.

**③ 다른 은행 이름을 지어냈다.** KB국민은행 메뉴에 `"우리은행 돈 보기"`가 붙었다.
문구를 통째로 버렸더니 `"국민은행 잔액"`까지 날아가고 `"은행 잔고"` 같은 껍데기만 남아
**고치려던 것보다 나빠졌다.** 지금은 회사 이름만 떼어 낸다 — `"국민은행 잔액"` → `"잔액"`.

**④ 동의어가 문장이었다.** 사람이 쓴 것은 평균 4.4자인데 LLM은 6.7자였다. 파이프라인의
포함 판정은 짧은 말에 유리하다 — `"돈 얼마 있어"`는 질의 `"잔액"`을 포함하지도, 거기
포함되지도 않아 매칭이 0이다. 프롬프트에 "공백 빼고 2~7자"를 넣고 검증에서 9자를 넘는
것을 버리니 4.0자가 됐고, C가 20% → 31%로 올랐다.

### LLM을 색인에서 빼고 런타임으로 옮겼다 (2026-08-11)

앞 절의 결론은 "동의어를 미리 붙이면 해롭다"였다(85% → 67%). 미리 붙이는 방식은
**모든 가능한 표현을 미리 알아맞혀야** 하고, 빗나간 것들이 서로를 방해한다.

그래서 자리를 옮겼다. **LLM은 색인이 아니라, 사용자가 실제로 한 말을 보고 고른다.**

```
"계좌이체"     → 온디바이스가 잡는다. LLM 안 부름 (85%가 여기서 끝난다)
"돈을 보내다"  → 온디바이스 실패 → LLM에게 [발화 + 후보 20개] → 고른 것 제시
"날씨 어때"    → 온디바이스 실패 → LLM이 "없음" → 원래대로 되묻기
```

재현: `pnpm --filter @minui/enricher bench:assist`

| | 온디바이스만 | + 런타임 폴백 |
|---|---|---|
| 정답 있는 질의 75건 | 85% | **95%** |
| 답 없는 질의 100건 | — | **97건 옳게 거절** |

폴백이 푼 7건은 전부 <b>어휘가 없어서</b> 놓치던 것들이다.

```
"매달 빠져나가는 거"   → 자동이체내역 조회/해지/변경
"이체 한도 늘려줘"     → 이체한도 조회/감액
"잠자는 돈 있나"       → 휴면예금조회
"인증서 새로 받아야 해" → 인증서 발급/재발급
"수익 났나 보자"       → 기준가/수익률조회
```

잘못 들이민 2건도 적어 둔다. `"오늘 뉴스 좀 보여줘"` → 펀드뉴스(은행 앱에 뉴스가 있으니
아주 틀린 것은 아니다), `"우리 딸 전화번호"` → 휴대전화번호입금계좌지정(틀렸다).
둘 다 <b>후보로 제시될 뿐 자동으로 열리지 않는다.</b>

#### 비용 — 부를 일이 드물다

호출은 <b>정답 있는 질의의 15%</b>(11/75)에서만 일어났다. 나머지 85%는 온디바이스가
끝낸다. 호출당 441토큰이다. 답 없는 질의는 100% 폴백까지 가지만, 실제 은행 앱에서
"날씨 어때"를 치는 비율이 그만큼 높지는 않다.

#### 계약을 좁게 유지했다

`packages/core`는 한 줄도 고치지 않았다… 정확히는 **한 함수를 더했다**.
`engine.candidates(query, limit)` — 문턱 없이 추린 순위다. `search()`가 되묻기를 냈다는 것은
확신이 낮다는 뜻이지 순서가 없다는 뜻이 아닌데, 900개를 통째로 넘길 수 없고 카탈로그
순서로 자르면 관계없는 메뉴가 후보가 된다.

`MinUIProvider`가 받는 것은 함수 하나다.

```ts
assist?: (query: string, candidates: MenuId[]) => Promise<MenuId | null>
```

**엔진은 이것이 LLM인지 무엇인지 모른다.** 네트워크·API 키·모델 이름이 코어와 React
어디에도 들어오지 않는다. 없으면 지금까지와 똑같이 되묻고, `null`이면 되묻고,
호출이 실패해도 되묻는다 — <b>도우미가 죽어도 서비스는 100% 돈다.</b>

안전 경계도 그대로다. 도우미가 고른 것도 **후보로 제시될 뿐 자동 실행되지 않는다**.
목록에서 고르기만 하므로 없는 화면이 열리는 일이 구조적으로 불가능하고,
`riskLevel: high`는 §9.3이 따로 막는다.

#### API 키는 브라우저로 가지 않는다

`demos/src/assistRoute.ts`가 개발 서버에 `/api/assist`를 붙인다. 키는 서버에만 있고
브라우저는 질의와 후보만 보낸다. 클라이언트 코드에 키를 넣으면 누구나 개발자 도구에서
꺼내 쓸 수 있고, 그 순간 남의 한도로 남의 요금이 나간다.
배포할 때는 이 미들웨어가 서버리스 함수 하나로 바뀐다 — 하는 일이 같아 옮기는 비용이 없다.

#### 다음 — 푼 것을 동의어로 승격

폴백이 `"매달 빠져나가는 거"` → `자동이체내역 조회/해지/변경`을 풀면, 그것을 동의어로
적어 두면 **다음부터는 온디바이스가 잡는다.** 호출이 줄고 비용이 시간이 갈수록 내려간다.
지금까지 "동의어를 어디서 얻을 것인가"가 이 프로젝트의 벽이었는데, 그 답이
<b>실사용</b>이라는 것을 앞서 적어 두고도 경로가 없었다. 이 구조가 그 경로다.

### MinUI Studio — 링크 하나로 이식 (2026-08-11)

`/studio`에 금융사 주소를 넣으면 그 자리에서 쉬운 모드가 뜬다. 마지막 화면에 이식 코드
두 줄을 보여 준다 — 그것이 §7.2 계약 전부이고, 보는 사람이 직접 확인하게 하는 것이 목적이다.

실측:

| 사이트 | 수집 | 정리 | 첫 화면 | 합계 | 결과 |
|---|---|---|---|---|---|
| 하나은행 | 9.4초 | 0.0초 | 1.3초 | **10.7초** | 786 → 710개 |
| KB증권 | 4.2초 | 0.0초 | 1.1초 | **5.3초** | 1,443 → 665개 |

**반나절이 걸리던 일이 10초가 됐다.** 다섯 사이트를 손으로 만들 때는 사이트당 스니펫을
고쳐 가며 반나절씩 썼다.

#### 조립은 CLI와 **같은 함수**를 쓴다

`buildMenus`를 파일 입출력에서 떼어내 `tools/src/build-catalog.ts`에서 내보내고, Studio가
그것을 그대로 부른다. 갈래·이름 겹침·개인정보 검사·병합 순서가 전부 같다.
<b>미리보기가 실제 산출물과 다르면 미리보기가 거짓말이 된다.</b>

#### LLM은 첫 화면만 고른다

Studio에서 LLM이 하는 일은 <b>카드 넉 장 고르기 한 번</b>이다. 동의어 생성은 색인에 넣으면
해로웠고(85% → 67%), 뜻풀이는 600개를 기다리게 할 수 없어 CLI로 따로 돌린다.

**프리셋 품질은 그저 그렇다.** 하나은행에서 `해지계좌 조회`·`세금우대한도조회`를,
KB증권에서 `랩잔고조회`를 첫 화면에 올렸다 — 70대가 은행 앱을 열자마자 볼 것은 아니다.
호출 한 번짜리 판단의 한계이고, 카탈로그 순서로 채우는 것보다는 낫지만 사람이 고른
`sites.ts`의 프리셋에는 못 미친다. 이것도 가족 테스트로 재야 할 항목이다.

키가 없으면 카탈로그 순서로 채우고 Studio는 그대로 돈다.

#### Studio가 드러낸 것 둘

**① 아이콘이 전부 같았다.** 자동 수집 카탈로그는 아이콘 지정이 없어 카드 넉 장이 모두
📄였다. 그러면 <b>"큰 카드라 한눈에 알아본다"는 주장이 무너진다</b> — 글자를 읽어야만
구별되는 카드는 목록과 다를 바 없다. 손으로 고른 25개에서는 `overrides`에 아이콘을 써 둬서
드러나지 않았다.

`tools/src/icons.ts`에 라벨 규칙을 뒀다. **상품 갈래를 행위보다 먼저 본다** —
`대출계좌조회`는 잔액 화면이 아니라 대출 화면이고, `예금조회/추가입금`은 입금 화면이 아니라
예금 화면이다. 이름을 붙인 사람이 앞에 둔 명사가 그 화면이 다루는 것이다.
LLM에게 묻지 않았다. 금융 메뉴는 정해진 낱말을 쓰므로 규칙으로 충분하다.

**② 긴 이름이 카드 밖으로 샜다.** `금융상품개설내역/계약조회` 같은 열두 자짜리가 카드
테두리를 넘어 옆 카드 위로 흘렀다. 손으로 고른 짧은 이름에서는 안 보이던 것이다.
말줄임으로 자르지 않고 줄바꿈으로 처리했다 — 잘라 버리면 무엇인지 알 수 없게 되는데,
그것은 카드가 하려던 일의 반대다.

**둘 다 실제 사이트를 얹어 보지 않았으면 몰랐을 것들이다.** 손으로 고른 카탈로그는
알게 모르게 엔진에 맞춰져 있었다.

#### 로그인이 필요한 사이트

서버 수집이 못 보는 메뉴는 Studio도 못 본다(KB국민은행 3%). 그때는 브라우저 스니펫을
쓰라고 화면에 안내한다 — `services/harvester/out/harvest-snippet.js`.

## M6 — 어려운 말 풀이 (2026-08-14)

메뉴를 **찾는 것**과 그게 **뭔지 아는 것**은 다른 문제다. 기획안 §15가 증권 앱의 실제
장벽으로 지목한 것이고, 카드와 음성이 푸는 것은 앞엣것뿐이다. 도착해도 못 쓰면 도착한
것이 아니다.

### 만들어 놓고 안 쓰던 것을 켰다

`hint`는 이미 카탈로그에 있었다. `services/enricher/src/prompt.ts`가 생성하고
`build-catalog.ts`가 반영하는데 **어느 화면에도 나오지 않았다** — assist 프롬프트의 후보
설명으로만 쓰였다. 실제 커버리지:

| 사이트 | 메뉴 | 뜻풀이 | 커버리지 |
|---|---|---|---|
| KB국민은행 | 419 | 372 | 89% |
| KB증권 | 642 | 566 | 88% |
| 미래에셋증권 | 359 | 308 | 86% |
| 신한은행 | 930 | 745 | 80% |
| 하나은행 | 598 | 531 | 89% |
| **합계** | **2,948** | **2,522** | **86%** |

나머지 426개에는 런타임으로 묻는다(`/api/explain`). 검색 폴백과 같은 구조다 —
**온디바이스가 가진 것으로 안 될 때만** 부른다.

### 이름은 라벨로 두고 설명으로 붙였다

전체 메뉴에서 뜻풀이를 버튼 **안**에 넣으면 접근성 이름이 "메뉴명 + 한 문장"이 된다.
700줄짜리 목록에서 그러면 스크린리더로 훑어 나갈 수가 없다. 버튼 밖에 두고
`aria-describedby`로 연결했다. 카드에서는 반대로 안에 넣는다 — 넉 장뿐이라 이름이
길어져도 훑을 것이 없고, 오히려 읽어 주는 편이 낫다.

카드에서는 **답과 뜻풀이를 함께 쓰지 않는다**(P1). 답이 있으면 답만 보여 준다.
답이 있는 카드는 이미 사용자가 아는 메뉴이기도 하다.

### 30자 상한이 이 기능의 존재 이유를 잘라 냈다

**실패하고 고친 기록이다.** 런타임 풀이에 빌드 타임과 같은 30자 상한을 걸었더니:

| 용어 | 모델이 낸 풀이 | 길이 | 결과 |
|---|---|---|---|
| 반대매매 | 빌린 돈을 제때 갚지 못하면 주식을 강제로 팔아버리는 일이에요 | 34 | **버려짐** |
| 세금우대한도조회 | 세금을 적게 내는 혜택을 얼마나 더 쓸 수 있는지 알려줘요 | 32 | **버려짐** |
| 랩잔고조회 | 전문가가 대신 굴려주는 내 돈이 얼마인지 확인하는 곳이에요 | 32 | **버려짐** |
| 예수금 | 내 통장에 들어있어 언제든 쓸 수 있는 돈이에요 | 26 | 통과 |

모델이 낸 풀이는 전부 멀쩡했다. **어려운 말일수록 풀 말이 길어지는데, 상한이 하필
그것들만 걸러 냈다.** 쉬운 `예수금`만 통과했으니 규칙이 거꾸로 걸려 있었던 것이다 —
이 기능이 존재하는 이유가 바로 그 세 단어다.

상한을 둘로 나눴다(`services/enricher/src/hint.ts`). **묻지 않았는데 깔리는 것과 눌러서
받는 것은 다르다** — 빌드 타임은 700줄 목록에 두 줄씩 깔리면 안 되므로 30자를 유지하고
(기존 2,522개의 기준을 바꾸지 않는다), 사용자가 직접 물은 답은 45자까지 받는다.
검증 규칙(개인정보·이름 되풀이)은 두 경로가 같은 함수를 쓴다.

### 안전 경계

뜻풀이는 조회성 정보라 §9.3 밖이지만, 금융 앱 안에서 모델이 상품을 권하거나 투자 판단을
내리면 그것은 투자권유다. 프롬프트에 **상품 추천·투자 판단·구체적 금액 금지**를 박고,
박혀 있다는 것을 테스트로 굳혔다. 모델이 모르면 `null`이고 화면은 "뜻을 알 수 없었어요"라고
말한다 — **틀린 뜻풀이는 없는 것보다 나쁘다.**

키가 없으면 묻는 버튼 자체가 뜨지 않는다(불변규칙 9).

### 아직 안 한 것

**풀이 품질을 사람이 검수하지 않았다.** 위 표의 여섯 개는 내가 눈으로 본 것이지 측정이
아니다. 어려운 용어 상위 30개를 뽑아 사람이 맞다/틀리다를 매겨야 수치가 된다.
그때까지 "뜻풀이가 정확하다"고 말하지 않는다.
