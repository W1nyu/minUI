## M4 — 메뉴 검색 (2026-08-10)

### 1회 발화 정확 매칭 — DoD 75%

| 지표 | 결과 |
|---|---|
| 질의 | 50건 (구어체, `tools/fixtures/voice-queries.json`) |
| 메뉴 | 25개 |

| 되묻기 | 1/50 (2.0%) |
| 1순위를 올린 단계 | 정확 매칭 16 · 동의어 27 · 자모 보정 6 |

재현: `pnpm --filter tools bench:search`

> **이 수치를 그대로 믿으면 안 되는 이유.**
> 질의 세트를 내가 쓰고, 그 결과를 보고 카탈로그의 동의어를 보강했다. 기획안 §12.2-B가
> 의도한 피드백 루프("어떤 단어로 기능을 부르는가 → 동의어 사전에 반영")이긴 하지만,
> 같은 사람이 문제와 답을 함께 만든 셈이라 실사용 성능의 추정치가 아니다.
> 의미 있는 수치는 §12.2-B의 사용자 테스트에서 **처음 듣는 발화**로 다시 재야 나온다.
> 그때를 위해 이 세트는 고정해 두고 새 발화는 별도 파일로 쌓는다.

유일한 실패: `"주소 바꿔야 해"` → 되묻기.
`바꿔`와 사전의 `바꾸기` 사이 자모 유사도가 0.73으로 개입 하한(0.75)에 못 미쳤다.
하한을 낮추면 통과하지만 오탐이 늘어나므로 그대로 두었다. 활용형 처리는 M5의 조정 대상.

### 의미 매칭(n-gram TF-IDF)의 기여 — **0**

같은 세트를 의미 매칭을 켜고/끄고 돌렸을 때 결과가 **완전히 동일**했다.

| 구성 | 1회 발화 정확 매칭 |
|---|---|
| 동의어 + 자모 + n-gram | 49/50 |
| 동의어 + 자모만 | 49/50 |

기획안 §14가 M4의 확인 항목으로 남긴 질문("경량 임베딩 모델을 넣을 가치가 있는가")에
대한 이 단계의 답은 **아니오**다. 이유는 두 가지로 보인다.

1. 문자 n-gram이 잡는 것(어간 조각 겹침)은 동의어 사전과 자모 보정이 이미 덮는다.
2. 문자 n-gram이 못 잡는 것(`돈`↔`금액`처럼 글자가 겹치지 않는 동의 관계)은
   문장 임베딩 모델이라야 잡히는데, 그건 이 구현체의 한계가 아니라 방식의 한계다.

곧 "임베딩을 문장 모델로 바꾸면 나아질 여지"는 남아 있다. 다만 그 여지를 사려면
**색인 29.6 KB → 모델 100MB대**를 지불해야 한다. 기획안 §14가 번들 크기를 리스크로
꼽은 판단의 근거가 이 수치다.

| | 크기 |
|---|---|
| n-gram 색인 (메뉴 25개, n-gram 473개) | **29.6 KB** |
| 다국어 문장 임베딩 모델 (최소 규모) | 100MB대 |

재현: `pnpm --filter tools build:index`

`EmbeddingProvider` 인터페이스는 그대로 둔다. 지금 값을 못 한다는 것과
교체 지점이 필요 없다는 것은 다른 이야기이고, 증권 앱처럼 메뉴가 수백 개가 되면
판단이 달라질 수 있다.

## M1 — 데모 계정계 (2026-08-10)

### 통합 테스트 — 실제 PostgreSQL (Testcontainers)

| 검증 항목 | 결과 |
|---|---|
| 이체 후 전 계좌 차변 합 = 대변 합 | 통과 |
| 같은 멱등성 키로 동시 10건 → 이체 1건 | 통과 |
| 같은 계좌 쌍 양방향 동시 이체 20건 → 데드락·음수 잔액 없음 | 통과 |
| 잔액 부족 → 분개·이체·멱등성 기록 모두 롤백 | 통과 |
| 동시 출금 10건(각 30만원, 잔액 100만원) → 정확히 3건만 성공 | 통과 |
| 같은 키 + 다른 내용 → 409 거절 | 통과 |

재현: `docker compose -f backend/compose.yaml up -d && cd backend && ./gradlew test`

### HTTP 레벨 실측

같은 멱등성 키로 동시에 10건을 보냈을 때:

```
201 200 200 200 200 200 200 200 200 200
```

`201`(새로 처리) 하나에 `200`(이전 결과 재생) 아홉. 수취인 잔액은 한 번치만 늘었다.

전 계좌 잔액을 전(錢) 단위 정수로 합산한 결과 **정확히 0**. 자본 계정이 발행 총액의
음수를 들고 있고 나머지가 그 반대편에 있다 — 원장 밖에서 생긴 돈이 없다는 뜻이다.

### 이 단계에서 잡은 설계 오류 세 가지

1. **격리 수준을 REPEATABLE READ로 잡았던 것.** 직관과 반대로 이것이 틀렸다.
   PostgreSQL의 REPEATABLE READ는 트랜잭션 첫 문장에서 스냅샷을 고정하므로, 락을
   기다리던 두 번째 이체가 앞 트랜잭션이 방금 커밋한 출금 분개를 보지 못해 초과 인출이
   난다. READ COMMITTED로 바꿔야 락을 얻은 시점의 잔액이 보인다. 직렬화는 격리 수준이
   아니라 비관적 락이 맡는다.

2. **멱등성 검사를 락보다 먼저 한 것.** 같은 키의 두 요청이 나란히 "처음 보는 키"라고
   판단한 뒤 락 앞에 줄을 서면, 앞 요청이 커밋해도 뒤 요청은 그 사실을 모른다.
   실제로 동시 10건이 전부 이체를 만들어 냈다. 락을 먼저 잡으면 뒤 요청은 앞 요청이
   커밋한 뒤에야 검사에 도달한다.

3. **`save()`가 INSERT가 아니라 merge로 나간 것.** ID를 직접 할당하는 엔티티에
   Spring Data의 `save()`를 쓰면 "있으면 UPDATE"가 되어 기본 키 제약이 발동하지 않는다.
   중복 차단 장치가 있는데 조용히 덮어쓰고 있었다. `Persistable.isNew()`로 진짜
   INSERT가 나가게 했다.

세 가지 모두 **동시성 테스트가 없었으면 드러나지 않았을** 것들이다. 단위 테스트나
수동 클릭으로는 전부 정상으로 보인다.

## M5 — 계측과 개인화 측정 (2026-08-10)

재현: `pnpm vitest run --project frontend test/scenarios` → `pnpm --filter tools simulate`
→ `pnpm --filter tools report`

### 이 측정이 무엇이 아닌지 먼저

기획안 §12.2는 **사람 8명**(60대 이상 5, 40~50대 3)의 사용자 테스트를 설계해 두었다.
그것은 하지 않았다. 여기 있는 것은 **스크립트 자동 수행**이고, 스크립트는 망설이지 않고
헤매지 않고 글자를 읽는 데 시간을 쓰지 않는다.

그래서 §12.1의 1차 지표 네 개 중 **탭 횟수 하나만** 나온다. 나머지 셋(완료 시간, 완료율,
오탐색률)은 빈칸으로 둔다. 스크립트가 만든 숫자를 그 자리에 넣으면 표 전체가 거짓이 된다.

탭 횟수를 재는 것이 그래도 값어치 있는 이유는, 그것이 사람이 아니라 **UI 구조의 성질**이기
때문이다. "이 화면에서 이 일을 끝내려면 최소 몇 번 눌러야 하는가"는 사용자 테스트 없이도
지금 확정할 수 있다.

### 1차 지표 — 탭 횟수 (목표: 기본 UI 대비 50% 감소)

| 과제 | 쉬운 모드 | 기본 UI | 차이 |
|---|---|---|---|
| S1 반복 이체 | 3 | 3 | **0%** |
| S2 잔액 확인 | 0 | 0 | 동률 |
| 이체 한도 변경 | 2 | 3 | −33% |
| 인증서 관리 | 2 | 3 | −33% |
| 해외 송금 | 2 | 3 | −33% |

S3 자동이체 관리는 경로가 셋이라 따로 잰다.

| 경로 | 탭 |
|---|---|
| 쉬운 모드 · 전체 메뉴 | **3** |
| 쉬운 모드 · 음성 | 4 |
| 기본 UI · 메뉴 트리 | 4 |

**목표 50% 감소는 달성하지 못했다.** 최대 33%이고, 대표 시나리오 S1·S2에서는 차이가 0이다.

### 왜 0인가 — 기획안의 기준선 가정이 과했다

기획안 §5.2는 기존 UI의 이체를 **탭 5회**(홈 → 전체메뉴 → 이체 → 계좌이체 → 최근 목록 →
대상 선택)로 잡았다. 그런데 현대 은행 앱은 홈에 이체 바로가기와 계좌 잔액을 이미 올려 둔다.
대조군을 실제 앱처럼 만들었더니 S1은 3탭, S2는 0탭이었다 — 쉬운 모드와 같다.

이것은 MinUI가 못해서가 아니라 **기준선이 §5.2의 가정보다 좋기 때문**이다. 그리고 이 사실
자체가 기획안 §2.2의 주장과 일치한다: 실패는 *자주 쓰는 기능*이 아니라 *찾아야 하는 기능*에서
일어난다. 자주 쓰는 것은 어떤 앱이든 이미 홈에 있다.

차이가 나는 곳은 꼬리다 — 홈 바로가기에도 카드에도 없는 메뉴에서 일관되게 1탭(−33%)이
줄어든다. 쉬운 모드의 전체 메뉴가 25개를 한 목록에 펼치는 반면 기본 UI는 카테고리를 한 번
펼쳐야 하기 때문이다.

### 탭 횟수가 잴 수 없는 것

**탭 횟수는 난이도의 하한이고, 조밀한 UI에 유리하게 편향된다.** 기획안 §2.2가 말한 비용은
탭 자체가 아니라 매 단계의 "다음에 뭘 눌러야 하지"라는 판단이다. 배너와 8칸 아이콘 격자와
5개 탭바가 있는 홈에서 이체 버튼을 찾는 시각적 탐색 비용은 이 표에 한 글자도 반영되지 않는다.

음성 경로가 탭 수로는 4탭(기본 UI와 동률)인 것도 같은 이유다. 음성이 없애는 것은 탭이 아니라
**"자동이체 관리가 어느 카테고리에 있는지 알아야 하는 부담"**이다. 그것은 사람을 앉혀 놓고
재야 나온다.

### 2차 지표 — 카드 적중률과 배치 안정성

120일 사용 패턴 시뮬레이션. 목표는 적중률 70% 이상, 주당 교체 1회 이하.

| 페르소나 | 설정 | 카드 적중률 | 주당 교체 | 수렴 |
|---|---|---|---|---|
| A 김순자 (73세) | 기본 | **100.0%** | **0.00** | 변화 없음 |
| B 박현우 (46세) | 기본 (마진 20% · 1회 1장) | 50.0% | 0.29 | 61일 |
| B | 1회 2장 | 62.5% | 0.23 | 40일 |
| B | 마진 10% / 50% / 쿨다운 12h | 50.0% | 0.29 | 61일 |

**배치 안정성은 목표를 크게 넘겨 달성**했다(0.00~0.29 ≤ 1.0).
**카드 적중률은 페르소나에 따라 갈린다** — A는 100%, B는 50%로 목표 미달.

세 가지가 드러났다.

**1. 프리셋이 맞는 사용자에게 개인화는 아무것도 하지 않는다 — 그리고 그게 옳다.**
A는 120일 동안 카드가 한 번도 바뀌지 않았다. 안정화 장치가 "할 일이 없을 때 아무것도 하지
않는" 것이 원칙 P3의 실제 모습이다.

**2. 수렴이 느리다. 발목을 잡는 것은 파라미터가 아니라 세션 빈도다.**
B가 자리를 잡는 데 61일이 걸렸다. 마진을 10%로 낮춰도, 50%로 올려도, 쿨다운을 12시간으로
줄여도 **결과가 똑같았다**. B는 앱을 한 달에 네다섯 번 열고, 재배치는 세션당 한 번뿐이므로,
24시간 쿨다운은 애초에 걸리지도 않는다. 저빈도 사용자에게 부족한 것은 시간이 아니라 세션이다.

**3. 20% 마진은 프리셋→개인화 전환 구간에서 아무 일도 하지 않는다.**
프리셋 카드는 사용 기록이 없어 점수가 0이고, `0 × 1.2 = 0`이라 양수 점수를 가진 도전자는
마진과 무관하게 이긴다. 마진이 실제로 작동하는 곳은 양쪽 다 점수를 가진 **정상 상태의
재순위**뿐이다. 이것은 결함이 아니라 파라미터의 유효 범위이며, 기획안 §8.2를 읽을 때
그렇게 이해해야 한다.

### 파라미터를 바꾸지 않기로 했다

시뮬레이션은 `maxSwapsPerRecompute: 2`가 B에게 두 지표 모두에서 낫다고 말한다
(적중률 50%→62.5%, 주당 교체 0.29→0.23, 수렴 61일→40일). 교체를 빨리 끝내면 중간에
들락날락하는 카드가 줄어 총 교체 수까지 적어진다.

그럼에도 기본값을 1장으로 둔다. 이유는 두 가지다.

- 기획안 §8.2가 이 값의 조정 근거로 **사용자 테스트**를 지목했다. 카드가 하루 두 장 바뀌는
  것의 비용은 고령 사용자가 얼마나 혼란스러워하는가이고, 그것은 시뮬레이션이 매길 수 없는
  가격이다. 내가 만든 페르소나 두 명으로 P3에 직결된 값을 바꾸는 것은 근거를 넘어선다.
- 이 시뮬레이션의 사용 패턴은 내가 지어낸 것이다. 실제 사용 로그가 생기면 그것으로 다시
  재야 한다.

바꾸지 않았다는 사실과 그 이유를 남기는 것이, 수치가 좋아 보인다고 바꾸는 것보다 정확하다.
